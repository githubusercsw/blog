让 AI 助手"不失忆、不跑偏"：一次浏览器扩展开发的人机协作上下文工程实录

引子：一次让我惊讶的开发体验

前阵子我做一个 Chrome 扩展（把腾讯元宝的 AI 对话一键写进 Anki），和 AI 助手协作开发了整整一天。过程比我预想的顺畅太多——不是因为它”更聪明”，而是因为我们无意间把**”上下文管理”这件事本身当成了工程来做**。

事后复盘，我越想越觉得这套协作机制值得单独写一篇。它不教你怎么写扩展，而是讲：人类和 AI 助手一起做一个复杂任务时，怎么让 AI 记住该记的、不跑偏、不被会话长度拖垮、出了 bug 还能快速定位。

这篇文章以这次开发的过程细节为基底，拆解我们是怎么一步步用好这套机制的，以及以后怎么把它做得更好。

一、最大的敌人：失忆

先讲清痛点。LLM 助手的”记忆”和人类不一样：

  • 它没有真正的长期记忆，靠的是会话上下文（一段临时对话）。
  • 上下文有长度上限，长了会压缩、会截断、会丢失。
  • 每次会话结束，它对这段工作的印象就”清零”了。

这意味着：如果每个阶段都要从头讲一遍背景，协作成本会爆炸；如果上下文一长就开始”糊”，前面定好的决策就会悄悄走样。

所以我一开始就定了个原则：把上下文当成一种会丢失、要主动管理的资源，而不是”反正 AI 会记住”的默认假设。

二、机制总览：五件套

这套协作跑下来，我觉得核心是五样东西，缺一不可：

  1. 核心记忆修正：协作规则的”宪法”，由人亲自定。
  2. 文件系统扩展内存：把关键状态固化到磁盘，对抗失忆。
  3. 主线 / 分支管理：任务隔离，互不污染。
  4. 索引指针：一个文件就能”秒恢复”全部状态。
  5. 迭代反思：每一步都留痕，避免重复犯错。

下面逐个讲，并说明在这次开发里它们是怎么起作用的。

三、核心记忆：协作规则的”宪法”

这是我全程印象最深的一点。开发进行到一半，我发现 AI 助手在”如何配合我”这件事上偶尔会跑偏——比如风格、确认习惯、要不要先问再动手。这时候我做的不是一次次口头纠正，而是**直接动手修改它的”核心记忆”**。

这个核心记忆是 AI 每轮对话都自动加载的短规则（怎么称呼、沟通风格、协作时要不要先确认、我纠正过的行为）。我把对这次协作最重要的几条规则写进去，相当于给它立了本”宪法”。

效果立竿见影：之后它在多数场景下自动按规则行事，不需要我反复叮嘱。这比”你说一句我记一次”高效太多——因为规则沉淀在机制里，而不是散落在对话里。

可复用启发：和人协作一个长期项目，第一次发现”配合方式”问题，就把它固化进规则/文档，而不是靠每次提醒。

四、文件系统扩展内存：把状态固化到磁盘

AI 助手的记忆会丢，但磁盘不会。这是我们协作的关键设计：在工作目录里建了一个 _memory/ 文件夹，当作”文件系统扩展内存”。

它不是流水账，而是结构化的，分几个文件各司其职：

  • INDEX.md：总索引，项目全局状态、该读哪个文件、当前到哪一步。
  • phases.md：阶段状态与进度。
  • decisions.md：用户已确认的决策。
  • reflection.md：每次迭代的”思考-执行-反思”留痕。
  • runbook.md：如何验证、如何继续开发。

这套东西的威力在”上下文压缩“那一刻完全体现：当对话已经很长、信息密度过高时，我让助手把当前状态全部固化到 _memory，然后压缩上下文。压缩之后，新的一轮对话只需读 INDEX.md 就能完整接上——之前几小时的进展一点没丢，就像从”失忆”里恢复了记忆。

五、主线 / 分支管理：任务隔离

多任务最怕纠缠。这次我们明确分了主线和分支：

  • 主线：扩展开发本身。
  • 分支：过程中插入的临时任务（比如写一份调研文档、写博客、压缩上下文等）。

规则是：分支任务尽量不占用主线的上下文。分支的产出固化到自己的文件/位置，干完就回到主线，主线继续走。

效果：插入的临时任务没有把主线搞乱，主线状态始终清晰。这就像 git 的分支——功能分支互不干扰，随时能 merge 回来。

六、记忆分层：不把鸡蛋放一个篮子里

助手的记忆系统我观察下来是分层的，这个分层很关键：

  • 核心层（core）：每轮必守的短规则（上面说的”宪法”）。
  • 知识层（wiki）：可检索的主题知识（项目、实体、经验、方法）。
  • 源文件层（raw）：外部资料的”溯源凭证”（指向原始文件/链接，不存全文）。

为什么要分层？因为不同内容有不同生命周期：

  • 规则要每轮加载 → 放核心层，且必须精炼（太长就没意义了）。
  • 项目知识要能检索 → 放知识层，按需读取。
  • 原始资料的全文不用每次都读 → 放溯源层，需要时再找原文。

可复用启发：任何”记忆”系统，都不要一锅烩。区分”每轮必带”、”按需查询”、”需要时溯源”三档，能省下大量不必要的上下文占用。

七、懒加载决策树 + 状态机

这是我给这次协作提炼的两个”运行模式”：

懒加载决策树：需要时才读

助手不是把所有知识一次灌进脑子，而是遇到需要判断时才去检索（决策树）。比如遇到”环境问题 vs 业务问题”、”该用哪个选择器”这类判断时，才去查对应的知识层。用多少，读多少，避免上下文被无关信息撑爆。

状态机：分阶段迭代

开发不是一口气冲到底，而是一个明确的状态机：Phase0 地基 → Phase1 环境 → Phase2 适配 → Phase3 把关 → Phase3.5 美化 → Phase4 可靠性。每个阶段验证通过才进入下一阶段，当前状态明确记录在 phases.md。

这套状态机的价值在”防连锁问题”：每层都真实验证过，出了问题能立刻定位是哪一层的锅，而不是在混乱里猜。

八、以本次开发为例：六个阶段怎么用这套机制

  • 设计阶段：先定”上下文工程”原则（失忆是敌人），再定技术架构（分层 + 依赖注入 + 配置外置）。→ 用 核心记忆 定协作规则。
  • 环境阶段：探测 Anki、做依赖注入。→ 用 决策树 判断”环境问题 vs 业务问题”。
  • 适配阶段：抓元宝真实 DOM，做选择器配置化 + 自检。→ 用 状态机（选择器主/备降级）+ 把 DOM 结构结论沉淀进 知识层。
  • 把关阶段：预览确认 + 幂等提交。→ 把决策记进 decisions.md。
  • 美化阶段：内容转 Quizify 语法。→ 每一步 反思留痕（reflection.md）。
  • 可靠性阶段：补日志、降级、超时。→ 用 文件系统扩展内存 记录健壮性缺口。

贯穿全程的，是 INDEX 指针 + 分支管理 + 迭代反思 这三件套在兜底：状态永远能恢复，任务永远不纠缠，错误永远有迹可循。

九、这次协作里”机制救场”的几个瞬间

有几个具体瞬间，让我真切感到机制在起作用：

  • 压缩上下文后秒恢复：对话变长后压缩，新会话读 INDEX.md 立即回到主线，几小时进展零丢失。
  • 分支任务不污染主线：中间插入的写文档、写博客任务，都独立完成、独立交付，主线没乱。
  • bug 快速归因：一个按钮”只发最后一条”的 bug，因为分层清晰，很快定位到是”适配层的数据绑定”问题，而不是业务层。
  • 踩坑被记录下来：MV3 无 DOM、service worker 缓存、目标网站畸形 HTML……这些坑都写进了反思，同一个坑不会踩第二次。

十、对以后的启示：如何深化这套机制

如果下次还要做类似的长周期人机协作，我会把这套机制再深化：

  1. **把上下文工程当”一等公民”**：和代码一样重要，开工前先设计好。
  2. 核心记忆持续打磨：每次发现”配合方式”问题，就更新规则，让它越来越贴合。
  3. 记忆分层做精：知识层的页面粒度、关联、溯源要维护好，避免”记了却查不到”。
  4. 状态机更细：不只分阶段，还记录每个阶段的验证标准、可复现的测试。
  5. 沉淀可复用方法论：把这次总结成模板，以后同类项目直接套用。

结语

这次开发让我真正体会到：AI 助手和人协作，天花板不在于模型多强，而在于我们怎么管理它的”记忆”和”注意力”。

把上下文当成工程来管理——该记住的固化、该丢弃的放手、该检索的按需、该分层的隔离——人机协作就能从”每次重新认识”进化到”越配合越默契”。

这套机制的细节会随工具迭代而变，但底层的道理是稳的：再聪明的助手，也需要一套好的记忆系统，和一个会用好它的伙伴。

（本文基于一次真实的人机协作开发经历，记录可复用的协作方法论；具体工具机制以实际版本为准。）
