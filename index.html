Quizify Bridge 分阶段实战（十二）：规则审计与 LLM 差距——诚实地承认能力边界

Quizify Bridge 分阶段实战（十二）：规则审计与 LLM 差距——诚实地承认能力边界

日期：2026-09-03 · 系列终篇

摘要

规则引擎做到 139 个测试全绿后，最该做的一件事是：停下来问一句——它到底离”人”的理解差多远？ 本系列终篇讲规则审计的方法论与结论：用双轨对比量化规则与语义理解的差距，诚实标注能力边界，并给出收敛方向（LLM 兜底接口）。这是整个项目”元认知”的收束：不仅要知道系统能做什么，更要知道它不能做什么。

1. 为什么审计比写代码更重要

规则迭代到后期有个危险：测试全绿 ≠ 能力达标。测试是自证的（自己写规则、自己写断言），如果规则本身有系统性盲区，测试会一起盲。

审计的方法：外部基准——用语义侧的人工标注（理想结构）与脚本侧的实际输出对比，量化差距。

2. 审计结论：与 LLM/人工的差距

场景 规则侧 人工/LLM 差距
显式信号（序号/emoji/加粗） ~90% ~100% 小
列表项 vs 标题（上下文引导） ~60% ~100% 最大
隐式语义标题 ~50% ~95% 大
层级归位（嵌套结构） 无 ~100% 无规则实现

2.1 最大差距的根因：上下文缺失

“列表项 vs 标题”之所以差，是因为区分二者需要看上下文：

“① 输入密码”是列表项还是标题？答案是列表项——因为前一行”让用户去：”是引导行。规则侧虽然有”前一行尾冒号→列表项”的启发式，但覆盖不了所有引导形式（动词句引导、隐含列表等）。

2.2 层级归位：规则侧完全没有

“哪一行是 H1、哪一行是 H2”（嵌套层级）需要全局结构感知——规则侧目前只有”--- 后为 H1”和”强信号为 H2”两种粗糙推断。真实的层级关系（如”方案一/二/三”是并列 H2，其下还有子项）需要语义理解。

3. 双轨对比的量化方法

3.1 折叠数对齐率

每份样本：脚本折叠数 vs 语义期望折叠数。

3.2 标题命中率

脚本识别的标题中，多少与语义标注一致（含误报率）。

4. 诚实声明：已知边界（发布说明摘录）

  • 紧凑排版局限：真实网页文章标题后无空行时，弱信号不识别（auto-02 实证）。保守不破规则——放宽孤立段要求会大幅增加误判
  • 细粒度 vs 语义粗粒度：脚本按形态信号拆块，可能多于语义合并（auto-q02/q04/q08/q09/q10）——差异属粒度选择，非缺陷
  • 列表项 vs 标题：上下文引导场景识别率 ~60%

5. 收敛方向：两个 LLM 兜底接口

审计的产出不是”承认差距就完事”，而是设计收敛路径：

5.1 接口一：引导行/列表项复核

规则先给出”疑似标题”候选，LLM 复核”这个候选是标题还是列表项”——只处理规则置信度低的场景，不全程依赖 LLM。

5.2 接口二：层级归位

规则推断出标题集合后，LLM 对标题间的层级关系（H1/H2/H3）做全局归位——利用 LLM 的全文理解能力。

**为什么是”兜底”而不是”替代”**：规则零成本、确定、可测；LLM 有成本、不确定。主路径保持规则，兜底路径只在规则薄弱处调用 LLM——这是成本与能力的平衡点。

6. 规则 vs LLM 的哲学

维度 规则 LLM
成本 零 每次调用有成本
确定性 同一输入同一输出 概率性
可测性 完整单测覆盖 难以穷举
上下文感知 有限（行级启发式） 全文理解
适用场景 高频显式形态 低频模糊场景

结论：不是二选一，而是规则为主 + LLM 兜底。这个架构在 AI 应用开发中有普遍性——凡是”高频确定 + 低频模糊”的任务，都适合这个组合。

7. 全系列总结

从 M1 验证台到 M6 发布，十二篇手记回顾了 Quizify Bridge 的完整历程：

贯穿全程的三条纪律：测试全绿为门、环境持久化、上下文锚点。以及一个始终如一的认知：规则有边界，诚实标注边界，是可靠系统的一部分。

（系列完）

Quizify Bridge 分阶段实战（十一）：工程方法总结——测试门、持久化、上下文锚点

Quizify Bridge 分阶段实战（十一）：工程方法总结——测试门、持久化、上下文锚点

日期：2026-09-03 · 系列第十一篇

摘要

前十个阶段讲了”做什么”，本篇讲”怎么做”——贯穿全程的三条工程方法：测试全绿为门、环境持久化、上下文锚点。它们不是某个阶段的技术，而是让整个项目在长周期、多轮迭代、反复中断下仍能稳步推进的底层纪律。

1. 方法一：测试全绿为门

1.1 定义

每个里程碑以”验证台全绿”为门。任何阶段红，修复到绿再前进。

1.2 为什么它如此重要

“完成”这个词在软件开发里极其含糊。没有门，就会出现项目里真实发生过的现象：

  • 写文档替代跑验证：出了 6 个问题，团队选择写更多审计文档而不是修测试
  • 测试锁的与代码跑的不是同一套：StructureRouter 是死代码，测试却全绿
  • **”mock 全绿 ≠ 真实 DOM 全过”**：验证只在理想环境过，真实场景一跑就碎

测试门把”完成”变成可复现的度量：绿 = 有证据，红 = 有责任。

1.3 分层验证体系

层 定位 跑多久
L1 引擎单测 规则/结构推断（纯 JVM） 秒级
L2 结构统计 批量样本折叠统计 秒级
L3 全量回归 engine + app 全部单测 8-10 分钟

分层的关键收益：快反馈走 L1/L2，收口走 L3。日常迭代用秒级测试，里程碑用全量回归——不因”测试慢”而跳过，也不因”全量跑”而拖慢迭代。

2. 方法二：环境持久化

2.1 痛点

沙箱环境会被回收。JDK + Gradle + Android SDK + 依赖缓存共约 1.2GB，每次回收后重下，既慢又易失败（Google Maven 偶发 000）。

2.2 正确理解”持久化”

用户点名纠正过一个关键概念：

「持久化」= 把 JDK/Gradle/Android SDK/依赖缓存物理存放到不被回收的工作区目录，沙箱回收后工具链原样还在、零下载直接可用；脚本只负责首次搭建。

这区别于”脚本化重建”（每次回收后重下 1.2G 依赖）——后者看似自动，实则每次都在烧时间。

2.3 实现

用法：source /home/lingxi/workspace/.env/env.sh

3. 方法三：上下文锚点

3.1 痛点

Agent 上下文窗口有限，长项目必然经历多次压缩。压缩后”失忆”是最大的信息损失风险——曾有外部调研索引在压缩后”丢失”的教训。

3.2 解决方案：三层联动

3.3 锚点文件长什么样

STATE.md 包含：关键路径与命令、架构快照、规则引擎现状、测试分层现状、样本资产清单、本段结论与已知局限、待办队列。压缩后凭此文件 5 分钟恢复全部关键状态。

纪律：每次里程碑/压缩点前刷新锚点，保证它是新鲜的（而非一次写死的旧文档）。

4. 三方法的内在联系

三者共同回答一个工程问题：如何让一个长周期项目在资源有限（沙箱 2GB 内存/1 核）、环境易失（回收）、上下文易断（压缩）的条件下稳定推进？

5. 其他可复用经验

5.1 沙箱内存纪律

2GB 内存、1 核、无 swap：两个 gradle 并行会 OOM。单任务串行、Xmx 收敛到 1024m、禁用 daemon。

5.2 等待纪律

后台跑长任务（gradle 全量回归 8-10 分钟）+ 检查日志 BUILD 标记轮询，避免空转等待。

5.3 协作低效的五个根因

用户批评过”协作效率太低”，复盘出五个根因：反复全量重跑、await 空轮询、批次闭环不完整、结果不落盘、规则迭代凭感觉。对应解法：验证分层、日志标记轮询、批次沉淀纪律、结果落盘、样本双轨对比。

6. 结语

三条方法没有一条是”技术亮点”，但正是它们让 M1-M6 全程 139+37 个测试持续全绿、让每次中断都能快速恢复、让每个里程碑都能按时交付。工程能力 = 让”推进”可度量的能力。

Quizify Bridge 分阶段实战（十）：M6 真机端到端与发布——产品成立性验证

Quizify Bridge 分阶段实战（十）：M6 真机端到端与发布——产品成立性验证

日期：2026-09-03 · 系列第十篇

摘要

M1-M5 的全部验证都在沙箱/JVM 上完成，但项目最初的六大问题里有一条始终悬着：产品成立性未端到端验证——写入 AnkiDroid 从未真机成功。M6 就是补上这最后一块拼图：真机端到端 + 发布。本文讲真机验证的分工模型、版本号策略、以及”Agent 开发+静态验证；用户真机验证”的协作定案。

1. 真机验证的分工模型

沙箱无法渲染 Compose UI、无法调用 AnkiDroid API、无法体验剪贴板 toast。因此从一开始就定下分工：

Agent 开发 + 静态验证；用户真机验证。

验证项 归属 原因
引擎逻辑 / 规则 / 门禁 沙箱（L1/L3） 纯 JVM，秒级可测
UI 布局不变量 沙箱（L0b Robolectric） 锁死”按钮可见”等结构
剪贴板 toast 观感 真机 系统行为，沙箱不可见
暗黑模式观感 真机 渲染效果
写入 AnkiDroid 全链路 真机 依赖真机 AnkiDroid
R8 选择题渲染 真机 发布 blocker

这个分工让沙箱把能自动化的全部自动化，真机只留”必须人眼确认”的项——零环境成本，且观感项不阻塞开发迭代。

2. M6 真机端到端验证了什么

粘贴 → 解析 → 写入 AnkiDroid 全链路：

  1. 复制 AI 长文（如 HCI 专业解析）
  2. 打开 App → 剪贴板自动带入
  3. 引擎解析：结构推断 → 路由 → 折叠 → cloze → 门禁
  4. 选择/输入牌组、标签
  5. 保存 → AnkiDroid 数据库写入成功
  6. 在 AnkiDroid 中复习，确认卡片正确渲染（折叠/alert/表格/选择题）

3. 发布策略

3.1 版本号

版本 说明
0.1.0 初版雏形
0.2.0 M5.2 适配安卓 10+
0.3.0（本次） M6 正式版：三层引擎 + 分层接线 + UI 完善

bump 规则：versionCode 随大版本递增（2→3），versionName 语义化（0.2.0→0.3.0）。

3.2 发布产物

  • 正式版 debug APK（本地构建，沙箱已编译通过）
  • RELEASE_NOTES.md：变更 + 验证状态 + 已知边界
  • ROADMAP.md：M6 完成快照

3.3 诚实声明（发布说明中的已知边界）

发布说明不只是”功能清单”，还包含诚实的能力边界：

  • 紧凑排版局限（真实网页文章标题后无空行时弱信号不识别）
  • 细粒度 vs 语义粗粒度差异（脚本拆块可能多于语义合并）
  • LLM 差距（列表项 vs 标题 ~60%、隐式语义 ~50%）——两个 LLM 兜底接口留待后续

为什么要在发布说明里写局限：让用户对”哪些场景表现好、哪些会退化”有预期，避免把规则引擎当成万能的。

4. R8 选择题（发布 blocker）

计划书 P2-2 标注 R8 选择题卡真机验证是发布 blocker：选择题卡（;;; 语法 + 选项）必须验证在 AnkiDroid 正确渲染——因为它涉及 AnkiDroid 对 Quizify 选择题语法的支持，与模板/渲染相关，只能真机确认。

5. 协作流程复盘

整个 M6 的协作模式：

里程碑门：测试全绿为门 + 真机清单过。两者都满足才算 M6 完成。

6. 本阶段启示

“产品成立性”是任何项目的终局问题：规则再精美、架构再分层，写入 AnkiDroid 失败就是零。M6 把这件事从”悬而未决”变成”已实证”。而这一切的前提是 M1 立的纪律——测试全绿为门——让前九个阶段的所有成果都有据可依，真机验证只是最后一道确认，而不是从头开始排查。

Quizify Bridge 分阶段实战（九）：M5.4 UI 细节与样本固化——三次修正背后的测试思维

Quizify Bridge 分阶段实战（九）：M5.4 UI 细节与样本固化——三次修正背后的测试思维

日期：2026-09-03 · 系列第九篇

摘要

M5.4 看起来是”小修小补”：Back 输入框高度、cloze 文案、牌组下拉、样本 7/8 固化。但这一阶段暴露了最有价值的工程思维：用户报一个 UI 问题，背后往往是一类规则缺口。本文讲三处 UI 修正的取舍、样本 7/8 从”临时诊断”到”正式断言”的固化，以及”修一个测一类”的回归思维。

1. 三处 UI 修正

1.1 Back 输入框高度：从”随内容增长”到”固定上限”

用户反馈：Back 字段自动生成长文后，输入框无限变长，每次都要滚动很久才能看到下方解析设置。

根因：heightIn(min = 120.dp) 只设了下限——内容越长框越长，把设置区挤出屏幕。

修复：heightIn(min = 120.dp, max = 200.dp)——固定上限，比原文输入框（max=160dp）稍长，长文在框内滚动而非撑开页面。

1.2 cloze 文案：从”技术描述”到”用户语言”

用户反馈：「自动 cloze（tier1，可逐条核对）：」太技术化。

修复：「自动 cloze 这些~：」——用户视角的口语化表达。

1.3 牌组下拉：从”手输名字”到”API 读取”

用户反馈：牌组目前只能手输，但 AnkiDroid API 明明可以读已有牌组。

实现：

  • 桥接层新增 getDeckList()：api.deckList.values.sorted() 返回已有牌组名
  • UI 用 ExposedDropdownMenuBox + 已有牌组列表渲染下拉
  • 降级设计：API 未启用/无牌组时，下拉显示”无可用牌组”，不阻塞纯文本输入

2. 样本 7/8 固化：从诊断到断言

2.1 之前的形态（临时诊断）

样本 7（Vaultwarden 部署长文）和样本 8（HCI 专业解析）之前的测试是 Trace*Test——只打印不断言：

这是”测试的假象”：测试通过，但什么都没锁住。

2.2 固化后的形态（正式断言）

样本 7 断言（Vaultwarden）：

  • 推断 8 个标题（1 H1 + 7 H2），含「整个流程，通俗翻译：」「方案一：最省事 — 买个域名（推荐）」「怎么解决 HTTPS？」
  • 折叠 8 开 8 闭（LIFO 闭合平衡）
  • tab 分隔表格修复为管道符表格
  • 折叠无平衡违规（RedlineChecker R5 不报）

样本 8 断言（HCI）：

  • 门禁 0 P0（用户曾实测 7 项 P0 拒绝写入 → R10 空行修复后的回归点）
  • 关键标题被识别（emoji 变体 🎨🔬 + 纯文本变体）
  • 折叠开闭平衡

3. 固化过程中的意外发现：三处规则缺口

把样本 8 固化为断言时，测试红了——不是测试写错，而是规则真的有缺口：

缺口 样本实证 修复
右引号收尾疑问式被误杀 「人机交互到底是什么：不只是”画界面”」 右引号排除移至疑问式判定之后
emoji 含引号疑问式被误杀 「🌍 为什么国内看似”不常见”」 emoji 引号排除仅对无疑问词行生效
完整句后无空行标题漏判 「💡 完整句收尾。」后紧跟「HCI 的职业发展路径」 prevIsEmpty 放宽：前一行句读收尾视作段落边界

这正是”修一个测一类”的回报：固化样本 8 本意只是”把诊断变断言”，却意外揪出三个真实规则 bug——如果没有固化，这三个缺口会在真机上表现为”用户复制 HCI 长文没有折叠”。

4. 回归护栏

固化时同步补了两类回归护栏（防修复引入新误判）：

  • 「”记忆已固化。”」引号包裹正文句 → 仍不误判为标题
  • 「✅ 上一轮你说：”…”」emoji 加引号引用行 → 仍不误判为标题

5. 验证

  • L3 全量回归：engine 139 + app 37 全绿 0 失败
  • BatchInferenceTest 27 项（新增 5 用例 + 2 护栏）
  • UI 布局测试（Robolectric）全绿

用户报的每一个”小问题”，都值得用测试锁死。三处 UI 修正看起来是”顺手改改”，但样本固化揭示的规则缺口证明：没有测试的地方，就有潜藏的 bug。把用户反馈转成断言，是产品从”能用”到”可靠”的分水岭。

Quizify Bridge 分阶段实战（八）：样本工程——双轨对比驱动的规则迭代

日期：2026-09-03 · 系列第八篇

摘要

规则不是设计出来的，是喂出来的。标题识别规则体系迭代了四轮（P0-P3），每一次迭代都由真实样本驱动：脚本侧批量跑规则，语义侧人工标注理想结构，双轨对比暴露差距，再把差距沉淀成规则或测试。本文讲这套”样本工程”方法——它让规则迭代从”凭感觉”变成”可度量”。

1. 为什么需要样本工程

规则系统最大的风险是过拟合与漏识别并存：

  • 只盯着一个样本调规则，换个样本就崩
  • 没有基线度量，”改了没改好”只能靠感觉

解法：建立样本资产 + 双轨对比机制。

2. 样本资产

2.1 三批样本

批次 来源 样本 用途
第一批 用户真实复制 sample-01~06（六种 AI 平台格式） 金标回归基线
第二批 用户真实复制 sample-09~18（对话类） 批处理矩阵
自产批次 Agent 生成 auto-q01~q10（生活+技术问答）+ 2 篇真实文章 规则边界覆盖

2.2 样本形态覆盖

  • 表格三形态（管道/空格对齐/Tab）
  • 告警块丢 >、代码围栏丢语言标记
  • ASCII 框线图（卡片/思维导图/Mermaid/CSV/正则）
  • emoji 标题、§N 章节、第X轮/步、原则N
  • 紧凑排版（标题后无空行）

3. 双轨对比机制

3.1 两条轨道

3.2 对比矩阵

样本 脚本折叠数 语义期望 差异 结论
auto-q01 7 7 0 ✅ 对齐
auto-q03 2 5 -3 🔴 缺「步」识别
auto-02（真实文章） 0 10+ -10 🔴 紧凑排版局限
auto-q10 11 8 +3 🟡 细粒度差异

差异分析 → 归类（规则缺口 / 粒度选择 / 局限声明）→ 决策（修规则 / 记局限 / 留 LLM 兜底）。

4. 规则迭代闭环

4.1 实证迭代案例

轮次 样本实证 修复
P1 sample-09「第一轮：上下文工程」 ROUND_HEAD 补轮次
P1 auto-q03「第一步：先定总预算」 ROUND_HEAD 补「步」
P2 sample-11 引导句「两个主流技术选型：」 尾冒号先于疑问式排除
P3 sample-13「🤖 AGENT CONTEXT ENGINEERING — MACHINE-SPECIFICATION v1.0」44 字 emoji 放宽到 60 + 截断

4.2 批次闭环纪律

用户明确批评过”协作效率太低”，沉淀为批次纪律：

  1. 处理一批，沉淀一批（避免上下文压缩丢失）
  2. 问题-规则-测试一一对应（每个规则缺口有对应失败测试）
  3. 全量双轨对比（不抽样、不凭感觉）
  4. 结果落盘（analysis/24-29 文档 + 记忆系统联动）

5. 已知局限（诚实声明）

  • 紧凑排版零折叠（auto-02 真实文章）：标题后无空行时弱信号不识别。保守不破规则（放宽孤立段要求会大幅误判），记为 LLM 兜底接口输入
  • 细粒度 vs 语义粗粒度（auto-q02/q04/q08/q09/q10）：脚本按形态拆块可能多于语义合并——差异属粒度选择，非缺陷

6. 本阶段启示

**规则迭代的最高效路径不是”想更多规则”，而是”喂更多样本”**。双轨对比把”规则好不好”变成可量化指标（折叠数对齐率、标题命中率），驱动规则向真实分布收敛。这套方法也适用于任何”启发式规则 + 人工标注”结合的系统。

Quizify Bridge 分阶段实战（七）：标题识别规则体系 P0-P3——从强信号到揭示语法

Quizify Bridge 分阶段实战（七）：标题识别规则体系 P0-P3——从强信号到揭示语法

日期：2026-09-03 · 系列第七篇

摘要

剪贴板文本没有 # 标题标记，折叠又从哪来？答案：从文本形态推断标题。这是全项目最有技术含量的一章——用规则体系把”AI 长文里的标题”从正文中识别出来，精度逼近人工标注（显式信号 ~90%）。本文完整拆解 StructureInference v2 的规则体系：强信号、弱信号揭示语法、长度策略、以及八类正文误判排除。

1. 问题：无标记文本怎么找标题

AI 平台复制出的文本没有 Markdown 标记，标题和正文都是裸文本：

要折叠，必须先回答：哪一行是标题？

2. 信号分级：强信号 vs 弱信号

2.1 强信号（命中即折叠，无长度门禁）

有明确形态特征的标题，直接命中：

信号 模式 示例
序号标题 方案/步骤/方法…+序号 方案一：买域名
中文编号 一、/（一）/（二） 一、背景
章节号 §N §1 CONTEXT BUDGET
轮次标题 第X轮/章/节/阶段/部分/篇/步 第一步：理解需求
原则标题 原则N： 原则一：注意力优先
emoji 前缀 🎨/⚓/✅/❌/⚠️/❗… 🎨 建筑学迁移优势
加粗短行 xxx（≤30字） 核心结论
疑问式 含疑问词（什么/如何/为什么…） 我的疑问是什么

2.2 弱信号（纯文本短行 → 揭示语法）

无任何标记的短行（≤40 字），用”标题形态 vs 正文形态”判定。

3. 揭示语法：标题像什么，正文像什么

灵感来自语言学（主位-述位理论 + 中文标题正则研究，HoWToBench / CY-T 35-2001）。

3.1 标题形态（判为标题）

  • 疑问式短语：「我的疑问是什么」「怎么解决 HTTPS？」
  • 名词性收尾：「HCI 的职业发展路径」「给你的选择建议」
  • 4~14 字孤立名词短语：「Agent 协作红绿灯」

3.2 正文形态（判为正文，8 类排除）

# 形态 示例
1 句读收尾（。，；…含右引号） “记忆已固化。”
2 口语/体标记收尾（了/着/过/吗/呢/吧/的） 明白了 / 做完了
3 尾冒号引导行（先于疑问式排除） 两个主流技术选型：
4 连接词/转折词开头（但是/所以/如果…） 但是这样做不行
5 叙事主体开头（我们/大家/这些…） 我们要先理解
6 动词/介词引导（适合/通过/需要/指定了/提出了…40+） 指定了验证方法
7 枚举前缀（Tier/Level/Phase/Round）、阿拉伯列表、把字句、含连接符号 向量 + 知识图谱混合
8 定义句（：+斜杠枚举）、这/那+是/有/在判断句 四层记忆架构：工作 / 情景 / 语义 / 程序

3.3 判定顺序（关键）

两个顺序陷阱（样本实证）：

  1. 尾冒号必须先于疑问式：「两个主流技术选型：」含冒号是引导行，若疑问式先判定会误判
  2. 右引号必须在疑问式之后：「人机交互到底是什么：不只是”画界面”」含疑问词是标题，若右引号先排除会误杀

4. 长度策略：能制卡 > 标题完美

初始规则”超长标题直接拒绝”被用户纠正：

能制卡 > 某一个标题不完美——命中即折叠，超长只影响展示，不影响生成。

  • 弱信号软护栏 40 字（超过不判弱信号，但强信号不设限）
  • emoji 标题放宽到 60 字
  • 超长标题：截断展示而非拒绝写入

5. 上下文辅助规则

  • 前一行尾冒号 → 本行按列表项处理（引导行后的行为短行）
  • --- 分隔线后 → 一级章节（H1）
  • 前一行完整句收尾（句读） → 视作段落边界，允许后一短行为标题（样本 08 实证）

6. 与 LLM 的差距（诚实审计）

场景 规则侧 人工/LLM
显式信号（序号/emoji/加粗） ~90% ~100%
列表项 vs 标题（上下文引导） ~60% ~100%
隐式语义标题 ~50% ~95%
层级归位（嵌套） 无 ~100%

最大差距：列表项 vs 标题（需要上下文理解）、层级归位（需要全局结构感知）。收敛方向：两个 LLM 兜底接口（引导行/列表项复核 + 层级归位）。

7. 验证

  • BatchInferenceTest 27 项（含每类信号的命中 + 8 类排除的回归护栏）
  • 全量回归：engine 139 全绿
  • 样本批处理双轨对比（脚本 vs 语义）驱动规则迭代

8. 本阶段启示

规则系统的天花板是”形态特征”，LLM 的天花板是”语义理解”。规则的优势是确定性、零成本、可测试；LLM 的优势是上下文感知。成熟的方案不是二选一，而是规则为主 + LLM 兜底——规则覆盖高频显式场景，LLM 处理规则覆盖不了的上下文场景。

Quizify Bridge 分阶段实战（六）：M5.3 分层接线——把断开的链路真正接起来

日期：2026-09-03 · 系列第六篇

摘要

前五篇的引擎、UI 各自就绪，但存在一个致命问题：App 的 regenerate() 只跑引擎管线，从未接线 StructureRouter——路由是死代码。用户实测 Vaultwarden 样本”应该有折叠却没有”，正是链路断开的直接证据。M5.3 的核心工作：CardConverter → StructureInference → StructureRouter → Pipeline 全链路接线，并解决”剪贴板长文本必须有折叠”这一核心诉求。

1. 断链根因：测试锁的与代码跑的不是同一套

诊断发现：

  • 测试锁的是 StructureRouter（R0-R3 路由规格）行为
  • 但 regenerate() 实际只跑 engine Pipeline
  • 路由从未接线（StructureRouter 是死代码）

这是典型的”测试与实现脱节”：测试绿，不代表产品行为对。也解释了用户”Back 字段自动更新是路由的关系，并没达到理想效果”的反馈。

2. 接线后的全链路

2.1 R0-R3 路由规格

路由 判定 处理
A_FLAT 无结构信号 蓝本 toQuizify 栈式折叠
B_ALERT 含警示词（注意/警告/必须…） Router 生成 alert 模板
C_TABS 对比词 + ≥2 子标题 Router 生成 tabs 模板
D_NESTED # 与 ## 共存 蓝本 2 层 ::: 嵌套折叠

关键约束：B/C 由 Router 生成（特殊模板），A/D 由蓝本 toQuizify 折叠（避免双重处理）。

2.2 折叠的 LIFO 闭合

Quizify 折叠 ::: 是 LIFO（后进先出）配对：

  • 嵌套 ≤2 层（B1 建议上限）
  • 闭合顺序严格逆序，乱序会结构错乱
  • 无法提取到警示行时降级 A（保守）

2.3 containsStructuralFold：围栏感知

旧实现 contains(":::") 全文误判——代码示例里的 ::: 字面量会让整个文档跳过转换。修复为围栏外扫描：``` 围栏内的 ::: 不算结构标记，且 > [!TYPE] 也算”已是 Quizify MD”信号。

3. 剪贴板长文本的折叠诉求

用户明确对齐过：

长文本必须要有折叠——这是 Anki 记忆的最小原子单元，没有折叠的卡片等于一坨无法复习的文本。

这驱动了两个设计：

  1. 强信号命中即折叠：序号/emoji/加粗/§N/第X轮/原则N 等明确标题信号，直接折叠
  2. 弱信号揭示语法：纯文本短行用”标题形态 vs 正文形态”判定（下一篇详述）

4. 验证

  • CardConverter → Pipeline 全链路单测（含 D 路由两层嵌套折叠 + LIFO 闭合 0 P0）
  • 样本 7（Vaultwarden）全链路 trace：8 个折叠块，LIFO 平衡
  • L3 全量回归：engine 106 + app 33 全绿

5. 本阶段启示

“分层”只是架构图，接线才是架构本身。死代码再多层也是零。M5.3 的教训是：验证一个分层系统，必须测全链路端到端，而不是每层各自单测——各自绿不等于链路通。

Quizify Bridge 分阶段实战（五）：M5 引擎入库与 UI 三件套——从纯逻辑到可交互

日期：2026-09-03 · 系列第五篇

摘要

M1-M4 的解析引擎是独立工程（verification/），跑在 JVM 验证台上，与安卓 App 完全分离。M5 的任务是把引擎物理并入安卓工程成为 :engine 模块，并完成 UI 三件套：剪贴板读取、设置开关、暗黑模式。这是项目从”逻辑正确”走向”产品可用”的转折点。

1. M5.1 引擎入库

1.1 为什么必须入库

之前的引擎在独立工程 verification/，App 用不到它——这是”引擎双份代码漂移”的温床：App 里一套规则、验证台里另一套。用户实测”解析处 0 阶段”正是因为 App 从未接线到引擎。

1.2 决策：物理单源

两个候选方案：

方案 说明 判定
复制一份进 repo 保留 verification 独立 ❌ 双份漂移风险仍在
verification 并入 repo 作为 :engine 模块 物理单源 ✅ 推荐，采纳

最终 :engine 模块成立：纯 JVM（无 android.*），app 依赖 engine。迁移后以 repo 为唯一真源，verification 停更只读。

1.3 里程碑门

engine 模块测试 95/95 全绿（随迁断言套件不丢）——测试全绿为门的第一道实体闸门。

2. M5.2 UI 三件套

2.1 剪贴板读取

需求：用户复制 AI 长文后打开 App，应自动带入剪贴板内容，无需手动粘贴。

实现要点：

  • ClipboardManager 抽象可注入（测试友好）
  • 进入 App 即读剪贴板；仅当输入区为空时自动带入（避免覆盖用户已输入内容）
  • Android 12+ 系统强制 toast 提示（系统行为，无法关闭）
  • 无权限时回退到分享输入（复用 IntentHelper）

关键抽象：ClipboardSource 接口 + AndroidClipboardSource 实现，测试注入 mock。

2.2 设置开关（持久化）

需求：用户能开关增强层各能力（公式/alert/cloze/tabs）、cloze 激进档位等，且重启后保留。

架构：SettingsStore（DataStore 持久化）→ AppSettings 数据类 → Pipeline.Options 派生 → 引擎管线参数。

设置流的关键设计：开关改动即重跑解析，用户立刻看到效果，而不是”下次生效”。

2.3 暗黑模式

需求：支持跟随系统 + 手动强制。

实现：Material3 动态主题，isSystemInDarkTheme() + 手动开关（并入设置页）。darkMode=true 强制暗色，否则跟随系统。

踩坑：暗黑模式开启/不开启没效果——根因是缺少 Surface 兜底背景，暗色下浅字浅底看不清。修复：Surface(color = MaterialTheme.colorScheme.background) 包裹内容，两主题渲染正常。

2.4 输入框字体偏淡

用户反馈”输入框字体偏淡看不清”。这是 OutlinedTextField 的占位符/标签颜色在浅色背景下对比度不足的问题，调整后视觉对比度达标。

3. 验证

  • L0b Robolectric 全绿（EditorScreenLayoutTest 锁死”保存按钮不被挤出屏幕”不变量）
  • 开关→输出变化有断言
  • 重启后设置恢复有断言（DataStore 持久化）
  • 暗黑两主题渲染无崩溃

4. 本阶段启示

**UI 不是”画界面”，而是”可交互的状态流”**。M5.2 最大的架构收益是把 UI 状态与引擎管线解耦：UI 只管用户操作 → 状态变更 → 引擎重跑 → 展示结果，纯逻辑引擎保持可测。这为 M5.3 的”分层接线”（UI → 结构识别 → 路由 → 管线）铺平了道路。

Quizify Bridge 分阶段实战（四）：M4 增强层——蓝本没有的新能力

Quizify Bridge 分阶段实战（四）：M4 增强层——蓝本没有的新能力

日期：2026-09-03 · 系列第四篇

摘要

蓝本解决了”标准结构怎么定”，但用户实际使用中还有蓝本覆盖不到的场景：标签页（tabs）开放模式、公式统一体系、强调词扩展映射、cloze 收窄默认开。M4 增强层就是这些”蓝本没有的新能力”的落地点。与补全/蓝本层的保守不同，增强层允许激进——最多多包一层，内容无损。

1. 增强层四件套

1.1 tabs 开放模式（标签页）

蓝本只对”≥2 相邻代码块”触发 tabs。但 AI 回答里常见”短词+冒号”开头的对比段落（如”方案A：…\n方案B：…”），蓝本不识别。

增强层：任意短词+冒号 → 标签页，统一容器处理。风险可控——“最多多包一层代码框，内容无损”，与保守原则相符。

1.2 公式统一体系

AI 回答中的数学公式形态混乱：块级 $$、行内 $、化学式 \ce。增强层把它们统一接入公式渲染体系：

形态 处理
块级 $$ ... $$ 保留块级公式
行内 $ ... $ 行内公式
\ce{...} 化学式并入公式体系

1.3 强调词扩展映射（alert）

蓝本的 alert 四类（WARNING/IMPORTANT/CAUTION/TIP）用”词边界+120 字阀”触发。但用户场景有领域词：如医学里的”禁忌”应映射 WARNING。增强层提供扩展映射表：

词 类型
建议 / 推荐 TIP
务必 / 必须 WARNING
禁止 / 不要 CAUTION
补充 / 另外 NOTE
（用户可自定义领域词） …

这就是”规则配置化”的雏形——映射表外置，用户可以加自己的领域词。

1.4 cloze 收窄默认开

蓝本 fitb（填空题）默认关。但用户反馈”引号和书名号内的内容最适合做 cloze”（如”密码银行”）。增强层：cloze 仅对引号/书名号内容默认开启，避免过度挖空。

2. 分层原则的落实

这个原则直接决定增强层的实现风格：

  • tabs 开放模式：宁可多识别，不可漏识别
  • 公式：识别失败最多变纯文本，不破坏上下文
  • alert：词边界匹配，避免误伤普通文本

3. 与规则配置化（P1-2）的衔接

M4 已经为 M5 的”规则配置化”埋下伏笔：

  • alert 映射表 → 外置为 rules.toml 可编辑配置
  • tabs 触发词 → 配置化
  • 语言词典 → 外置

架构上，所有增强规则参数从 Rules.load() 读取，形成”L1 规则单一真源”——彻底消除 rules.md / verify_p0.py / RuleValidator.kt 三副本漂移。

4. 验证

  • 规则设计讨论 8 项定案逐条可测
  • 增强层 95/95 单测全绿（M4 里程碑门）
  • 四件套各自有针对性回归用例

5. 本阶段启示

**增强层的价值不在”功能多”，而在”边界清晰”**。蓝本权威负责标准结构，增强层负责蓝本没有的场景，二者通过分层原则隔离——激进增强永远不会破坏保守结构。这种”权威+扩展”的双层模型，是处理”标准与特例”关系的通用答案。

Quizify Bridge 分阶段实战（三）：M3 蓝本层——yuanbao2anki 权威规则的 Kotlin 移植

Quizify Bridge 分阶段实战（三）：M3 蓝本层——yuanbao2anki 权威规则的 Kotlin 移植

日期：2026-09-03 · 系列第三篇

摘要

补全层修好了输入，接下来要回答”结构怎么定”——答案来自蓝本：yuanbao2anki 的 markdown.js。M3 的核心是把这套经过实战检验的权威规则逐行移植成 Kotlin，并保留它的”语法红线”（静默退化陷阱的硬性校验）。本文讲移植方法、关键规则、以及”直通蓝本”与”增强层”的边界。

1. 蓝本是什么

yuanbao2anki 是 AnkiDroid 生态里把 AI 对话转成 Quizify 卡片的成熟方案，其 markdown.js 实现了从 Markdown 到 Quizify 语法的完整转换。我们的项目叫 Bridge（桥），蓝本 = 桥的”设计图纸”。

但注意：蓝本的能力边界是网页 DOM。上一讲已说明，纯文本剪贴板输入需要补全层先修符号，蓝本才能发挥权威性。

2. 移植路线：从 JS 到 Kotlin

2.1 蓝本的核心函数链

2.2 移植策略

策略 内容
逐条断言 蓝本原版测试样例（11 个）转 JUnit 断言，保证行为一致
提取稿核对 216 行提取稿逐条断言
分层对照 每份样本标注”补全后 / 蓝本后 / 增强后”三态期望，防止移植偏差

2.3 蓝本规则要点（决策记录）

维度 蓝本行为 移植决策
总门槛 无结构信号 → 原样直出 采纳：有结构信号才加工，避免机械化观感
h3+ 折叠 不折叠原样 采纳：按蓝本，只折叠 h1/h2
tabs ≥2 相邻代码块 采纳：仅蓝本触发，不搞对比词启发式
列表≥2 > [!NOTE] 采纳：列表项转提示框
表格 直出 采纳：表格原样
强调词 Alert 四类+词边界+120 字阀 采纳：按蓝本
行内增强 reveal + 高亮 采纳
cloze fitb 默认关 收窄默认开：仅引号/书名号

3. 语法红线（RedlineChecker）：静默退化陷阱的硬校验

Quizify 语法有个反直觉特性：语法错误不报错，而是静默退化——折叠变纯文本、tabs 错乱、alert 漏内容。用户渲染出”错卡”而不自知。

RedlineChecker 就是这道防线，检查规则包括：

规则 检查内容 严重性
R1 :::: 与 === 同行混用 致命
R2 recite 块缺 %% 致命
R3 折叠开闭不平衡（LIFO 配对） 致命
R5 reveal 跨行 / 括号不配对 致命
T 系列 静默退化提示 需修

实现上分两类：折叠平衡（开闭计数 + LIFO 校验）与行内配对（reveal/fitb 括号、recite 百分号）。

4. 移植中的关键坑

4.1 ::: 与围栏的字面量冲突

代码示例里出现 ::: 字面量（如展示语法本身），旧实现 contains(":::") 会全文误判，导致整个文档跳过转换。修复：围栏感知扫描——只有围栏外的 ::: 才算结构标记。

4.2 嵌套折叠的 LIFO 闭合

Quizify 折叠 ::: 是 LIFO（后进先出）配对。蓝本处理 h1→h2 嵌套时，闭合顺序必须严格逆序，否则结构错乱。这个”LIFO 闭合 + 嵌套 ≤2 层”约束贯穿后续 M5.3 的路由设计。

5. 验证与产出

  • 蓝本 11/11 + 提取稿 216 行逐条断言全绿
  • RedlineChecker 对未闭合围栏反例实测拦截
  • 蓝本行为与增强层边界清晰化（蓝本权威 + 增强扩展）

6. 本阶段启示

“权威规则”不等于”复制代码”——移植过程中最花时间的不是翻译语法，而是理解每个规则背后的假设（输入是 DOM、h3 不折叠、列表转 NOTE…），并用测试把这些假设固化。假设不固化，下一轮迭代就漂移。
