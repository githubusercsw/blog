# Quizify Bridge 分阶段实战（一）：M1 JVM 验证台——测试全绿为门的第一块地基

> 日期：2026-09-03 · 系列定位：把 AI 长文自动转成 Quizify Markdown 卡片的 Android 应用，从零到发布的全过程拆解。

## 摘要

本系列按里程碑（M1→M6）逐篇复盘 Quizify Bridge 的真实构建历程。开篇讲最容易被跳过、却决定了整个项目成败的一步：**JVM 验证台**。它不是"测试脚手架"这种锦上添花的东西，而是"测试全绿为门"这一项目纪律的物理载体——没有它，后面所有"完成了"的说法都没有度量标准。

## 1. 为什么需要验证台

### 1.1 一个险些失控的项目背景

项目起点是一个"机械化雏形"：当时代码里有一套简单的规则（rules），但存在六个致命问题：

| # | 问题 | 后果 |
|---|------|------|
| 1 | 产品成立性未端到端验证 | 写入 AnkiDroid 从未真机成功 |
| 2 | 元根因悬空 | 写文档替代跑验证门 |
| 3 | 无 `#` 标题文本退化 | 剪贴板长文失去结构 |
| 4 | 规则三副本漂移 | rules.md / verify_p0.py / RuleValidator.kt 互相矛盾 |
| 5 | 验证门当前不可运行 | 沙箱 L3 坏，无自动化兜底 |
| 6 | R8 选择题真机验证挂起 | 发布 blocker |

其中第 2 条最要命：**团队在用"写更多文档"来回避"跑验证"**。这被称为"元根因"——诊断出了病，却在继续写病历而不是开药方。

### 1.2 纪律的确立：测试全绿为门

与用户对齐后确立了核心纪律：

> **每个里程碑以"验证台全绿"为门。任何阶段红，修复到绿再前进。**

这句话的深层含义是：**"完成"不是一个主观判断，而是一个可复现的度量**。后续 M1-M6 的全部迭代都在这条纪律下进行——这也是本系列反复出现的主题。

## 2. M1 做了什么：JVM 验证台搭建

### 2.1 目标与验收

| 项 | 内容 |
|----|------|
| 目标 | 搭建纯 JVM 测试环境，让蓝本规则可被自动化断言 |
| 验收门 | 蓝本原版 11/11 测试样例转 JVM 断言全绿；6 份真实样本作为回归金标 |
| 技术栈 | Kotlin 2.0.21 + JUnit5 + Gradle 8.10.2 |

### 2.2 关键决策：为什么是 JVM 而不是安卓模拟器

安卓模拟器在沙箱环境跑不动（需要硬件加速与大量内存），但解析引擎本身是**纯逻辑**——不依赖任何 `android.*` 类。于是把引擎抽成独立模块，全部逻辑在 JVM 上可测：

- 引擎模块 `:engine`：纯 Kotlin，零 Android 依赖
- App 模块 `:app`：只做 UI 与桥接，逻辑复用 engine

这个分层在后续 M5 阶段被证明是关键架构决策：**引擎的 139 个测试全部可以在 JVM 秒级运行**，无需真机。

### 2.3 验证台的内容

验证台不只是"能跑测试"，它包含三层资产：

1. **金标测试集**：6 份真实样本（sample-01~06），每份手工标注期望块分布（补全后 / 蓝本后 / 增强后三态），形成回归基线
2. **蓝本移植断言**：yuanbao2anki 原版 11 个有效测试样例转成 JUnit 断言
3. **验证分层**：

| 层 | 定位 | 命令 |
|----|------|------|
| L0a | 纯逻辑单测（无 android.*） | `:engine:test` |
| L0b | UI 布局快照（Robolectric） | `:app:testDebugUnitTest` |
| L1 | 规则单一真源 | rules.toml + 覆盖自检 |
| L2 | 写入硬拒（P0 违例） | `save()` 复检 |
| L3 | 安卓编译闸门 | `:app:compileDebugKotlin` |

## 3. 踩坑记录

### 3.1 Gradle 环境反复崩溃

沙箱环境 gradle 从 8.10.2 被系统升级到 9.3.0，且 Google Maven 拉包失败（返回 `000`）。这是"验证门当前不可运行"的直接原因。最终解法：

- 锁定版本：`gradle-8.10.2` 固定路径调用，不依赖 `gradle` 命令
- 隔离 `GRADLE_USER_HOME`：绕过全局破损的 `/root/.gradle/init.gradle`（含语法错误）
- 镜像加速：阿里云镜像 + JitPack 放最后

### 3.2 环境持久化的教训

最惨痛的教训是**环境每次重建**：沙箱回收后 JDK/Gradle/Android SDK 全丢，要重新下载 1.2GB 依赖。用户点名纠正：

> 「持久化」= 把 JDK/Gradle/Android SDK/依赖缓存物理存放到不被回收的工作区目录，沙箱回收后工具链原样还在、零下载直接可用；脚本只负责首次搭建。

此后所有工具链放 `/home/lingxi/workspace/.env/`，靠 `source env.sh` 一键加载。这成为后续所有里程碑零环境成本的前提。

## 4. 本阶段产出

- `:engine` 模块独立成立，纯 JVM 可测
- 验证分层体系（L0a/L0b/L1/L2/L3）定义完成
- 环境持久化机制建立（`.env/`）
- 金标测试集初步成型
