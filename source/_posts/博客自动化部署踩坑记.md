# 引言

最近我在搭建一个"Anki 素材 → 博文 → GitHub Pages"的自动化博文工作流，过程中连续踩了几个坑，从**自定义域名 404** 到**自定义域名只有 HTML 没有样式**，排查下来才发现问题都指向同一个根源——**配置与环境耦合**。

这篇文章把这些问题和修复思路完整记录下来，希望能帮到同样在用 Hexo + GitHub Pages 部署博客的朋友。

---

# 问题一：自定义域名突然 404

## 现象

博客原本可以正常访问，某次重新构建部署后，访问第三方域名提示：

```
There isn't a GitHub pages site here
```

而默认域名 `xxx.github.io` 却一切正常。

## 排查

GitHub Pages 的自定义域名，靠的是**发布分支根目录下的 `CNAME` 文件**（文件内容就是你绑定的域名）。

我检查后发现：
- GitHub Pages 配置里 `cname` 字段变成了空；
- 发布分支上的 `CNAME` 文件**不见了**。

## 根因

我的发布流程是 `hexo clean && hexo generate`，再用 `public/` 目录整体强制推送到 `gh-pages` 分支。

问题就在这里：**`hexo clean` 会清空 `public/` 目录**，而我的 `source/` 里没有 `CNAME` 文件，所以重建后的 `public/` 里也不含它。一强制推送，`gh-pages` 分支上的 `CNAME` 就被删除了。GitHub 检测到 CNAME 消失，就自动清掉了自定义域名配置。

> **教训**：不要依赖 GitHub Pages 设置页自动生成的 `CNAME` 文件——那个文件在下次 `hexo clean` + 部署时会被覆盖清掉。

## 修复

在 `source/CNAME` 里声明一行域名：

```
your-domain.com
```

这样每次构建，`CNAME` 都会自动进入 `public/`，随站点部署到发布分支，**域名从此不会再因重建丢失**。

# 问题二：自定义域名只有 HTML，没有样式

## 现象

自定义域名能访问了，但页面只有文字，**所有 CSS 样式都丢了**，看起来像没有加载主题。

## 排查

我打开浏览器开发者工具，发现样式文件全部 404。再看 HTML 里的静态资源引用，路径是这样的：

```html
<link href="/blog/css/style.css" rel="stylesheet">
```

而实际访问时，自定义域名下站点在根路径 `/`，对应的样式地址应该是 `/css/style.css`。

我实测验证：
- `https://your-domain.com/css/style.css` → **200**（样式实际存在）
- `https://your-domain.com/blog/css/style.css` → **404**（HTML 引用的正是这个）

## 根因

问题出在 `_config.yml` 里：

```yaml
url: https://xxx.github.io
root: /blog/
```

`root: /blog/` 让 Hexo 把**所有静态资源路径**都写成了绝对路径 `/blog/...`。

- 默认域名 `xxx.github.io/blog/`：路径匹配，样式正常；
- 自定义域名 `your-domain.com/`：GitHub Pages 在自定义域名下以**根路径**服务，但 HTML 还引用 `/blog/...`，于是样式 404。

**本质**：构建产物被 `root` 绑死，无法同时适配"子路径部署"和"根路径部署"两种访问方式。

## 修复

如果你以自定义域名为主，把配置改为：

```yaml
url: https://your-domain.com
root: /
```

重新构建后，HTML 里的资源路径变成 `/css/style.css`，自定义域名下样式就正常了。

> **核心原则**：`root` 和 `url` 必须与实际访问路径一致。它们属于"环境相关配置"，应该外置并在发布前校验，而不是写死在构建逻辑里。

# 问题三：GitHub 推送反复网络报错

## 现象

推送 `gh-pages` 时反复失败：

```
fatal: unable to access 'https://github.com/.../': GnuTLS recv error (-110): The TLS connection was non-properly terminated.
error: failed to push some refs
```

有时还会出现 `Error in the HTTP2 framing layer`。

## 根因与修复

这是 Git 客户端与 GitHub 之间 **HTTP/2 连接不稳定**导致的。改用 **HTTP/1.1** 后稳定通过：

```bash
git -c http.version=HTTP/1.1 push -f origin gh-pages
```

> 小技巧：在推送命令里显式指定 `http.version=HTTP/1.1`，可规避部分 HTTP/2 传输层的偶发错误。

# 问题四：git 锁文件残留

## 现象

推送被中断后，再次执行 `git add` 报错：

```
fatal: Unable to create '.../.git/index.lock': File exists.
Another git process seems to be running in this repository...
```

## 根因与修复

这是 git 崩溃/中断后残留的临时锁文件。确认没有其他 git 进程在跑后，删除锁文件即可恢复：

```bash
rm -f path/to/repo/.git/index.lock
```

# 问题五：云端环境不支持定时任务

## 现象

我想用 cron 每天自动发布博文，但当前运行在云上环境，**不支持创建定时任务**。

## 处理

- 云上环境无法直接挂 cron，需切换到支持定时任务的环境（如本地/服务器，或客户端"连接我的电脑"模式）；
- 工作流的**入口脚本保持通用**，外部 cron 只负责"到点触发"，业务逻辑全在脚本内，换环境即可复用。

---

# 根源反思：这些坑为什么一个接一个

回头看，这五个问题不是孤立的，它们都指向同一个根源——**工作流的"环境假设"与"业务逻辑"耦合**：

| 问题 | 根源耦合点 |
|------|-----------|
| 自定义域名 404 | 域名声明依赖了构建产物（CNAME 被重建清掉） |
| 样式丢失 | `root` 路径写死进构建产物 |
| 网络报错 | 传输层假设（HTTP/2） |
| 锁文件 | 中断处理不健壮 |
| 定时限制 | 运行环境假设 |

**修复原则**可以总结为四句话：

1. **配置外置**：域名、路径、凭证等环境项，从代码逻辑里剥离，集中声明；
2. **动态注入**：声明随构建/运行自动进入产物（如 `source/CNAME` → `public/CNAME`）；
3. **发布前校验**：CNAME、`root`、凭证都在发布前断言正确，缺失即中止；
4. **状态可重建**：素材库、状态文件都能由脚本重建，不依赖脆弱记忆。

---

# 结语

这些坑看似琐碎，但每一个都是"配置与环境耦合"的具体体现。把**环境假设外置 + 校验前置**后，工作流从"换个环境就崩"变成了"换环境只改声明"。

自动化部署的价值，不在于"一键跑通"，而在于**即使出了错，也能快速定位、安全修复、不产生连锁反应**。希望这篇踩坑记录能帮你少走弯路。
