# Quizify Bridge 分阶段实战（十一）：工程方法总结——测试门、持久化、上下文锚点

> 日期：2026-09-03 · 系列第十一篇

## 摘要

前十个阶段讲了"做什么"，本篇讲"怎么做"——贯穿全程的三条工程方法：**测试全绿为门**、**环境持久化**、**上下文锚点**。它们不是某个阶段的技术，而是让整个项目在长周期、多轮迭代、反复中断下仍能稳步推进的底层纪律。

## 1. 方法一：测试全绿为门

### 1.1 定义

> 每个里程碑以"验证台全绿"为门。任何阶段红，修复到绿再前进。

### 1.2 为什么它如此重要

"完成"这个词在软件开发里极其含糊。没有门，就会出现项目里真实发生过的现象：

- **写文档替代跑验证**：出了 6 个问题，团队选择写更多审计文档而不是修测试
- **测试锁的与代码跑的不是同一套**：StructureRouter 是死代码，测试却全绿
- **"mock 全绿 ≠ 真实 DOM 全过"**：验证只在理想环境过，真实场景一跑就碎

测试门把"完成"变成**可复现的度量**：绿 = 有证据，红 = 有责任。

### 1.3 分层验证体系

| 层 | 定位 | 跑多久 |
|----|------|--------|
| L1 引擎单测 | 规则/结构推断（纯 JVM） | 秒级 |
| L2 结构统计 | 批量样本折叠统计 | 秒级 |
| L3 全量回归 | engine + app 全部单测 | 8-10 分钟 |

分层的关键收益：**快反馈走 L1/L2，收口走 L3**。日常迭代用秒级测试，里程碑用全量回归——不因"测试慢"而跳过，也不因"全量跑"而拖慢迭代。

## 2. 方法二：环境持久化

### 2.1 痛点

沙箱环境会被回收。JDK + Gradle + Android SDK + 依赖缓存共约 1.2GB，每次回收后重下，既慢又易失败（Google Maven 偶发 000）。

### 2.2 正确理解"持久化"

用户点名纠正过一个关键概念：

> 「持久化」= 把 JDK/Gradle/Android SDK/依赖缓存**物理存放**到不被回收的工作区目录，沙箱回收后工具链**原样还在、零下载直接可用**；脚本只负责首次搭建。

这区别于"脚本化重建"（每次回收后重下 1.2G 依赖）——后者看似自动，实则每次都在烧时间。

### 2.3 实现

```
/home/lingxi/workspace/.env/
├── jdk-21.0.12.1+1       ← JDK 物理落盘
├── gradle-8.10.2         ← Gradle 物理落盘
├── android-sdk           ← Android SDK 物理落盘
├── gradle-home           ← 依赖缓存（GRADLE_USER_HOME）
└── env.sh                ← 一键加载所有环境变量
```

用法：`source /home/lingxi/workspace/.env/env.sh`

## 3. 方法三：上下文锚点

### 3.1 痛点

Agent 上下文窗口有限，长项目必然经历多次压缩。压缩后"失忆"是最大的信息损失风险——曾有外部调研索引在压缩后"丢失"的教训。

### 3.2 解决方案：三层联动

```
文件系统（详细）    STATE.md 压缩锚点：路径/架构/规则/测试/样本/待办
记忆系统（指针）    wiki 项目页 + 经验页 + raw 溯源索引
Git（历史）        每次里程碑提交推送，历史真相可追溯
```

### 3.3 锚点文件长什么样

`STATE.md` 包含：关键路径与命令、架构快照、规则引擎现状、测试分层现状、样本资产清单、本段结论与已知局限、待办队列。压缩后凭此文件 5 分钟恢复全部关键状态。

**纪律**：每次里程碑/压缩点前刷新锚点，保证它是新鲜的（而非一次写死的旧文档）。

## 4. 三方法的内在联系

```
测试全绿为门   ← 让"推进"有证据
环境持久化     ← 让"推进"可持续（不因环境重建而停摆）
上下文锚点     ← 让"推进"可恢复（不因压缩而失忆）
```

三者共同回答一个工程问题：**如何让一个长周期项目在资源有限（沙箱 2GB 内存/1 核）、环境易失（回收）、上下文易断（压缩）的条件下稳定推进？**

## 5. 其他可复用经验

### 5.1 沙箱内存纪律

2GB 内存、1 核、无 swap：两个 gradle 并行会 OOM。单任务串行、Xmx 收敛到 1024m、禁用 daemon。

### 5.2 等待纪律

后台跑长任务（gradle 全量回归 8-10 分钟）+ 检查日志 BUILD 标记轮询，避免空转等待。

### 5.3 协作低效的五个根因

用户批评过"协作效率太低"，复盘出五个根因：反复全量重跑、await 空轮询、批次闭环不完整、结果不落盘、规则迭代凭感觉。对应解法：验证分层、日志标记轮询、批次沉淀纪律、结果落盘、样本双轨对比。

## 6. 结语

三条方法没有一条是"技术亮点"，但正是它们让 M1-M6 全程 139+37 个测试持续全绿、让每次中断都能快速恢复、让每个里程碑都能按时交付。**工程能力 = 让"推进"可度量的能力**。
