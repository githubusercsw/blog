# 从 Step 1 到 Step 5：一套自动化博客工作流的搭建踩坑与技术沉淀

这篇文章，我打算不写"某个知识点"，而是完整记录**一套系统是怎么一步步搭起来的**。它的背景是：我长期用 Anki 积累了两千多张知识卡片，一直想让它"流动起来"——变成持续输出的博客内容，并且做到可复用、可交给任意 Agent 无人值守地跑。

于是有了 `daily-blog-pipeline` 这套双层流水线。整个过程从 Step 1 走到 Step 5，每一步都有踩坑，也有值得沉淀的技术判断。下面按步骤讲清楚。

---

# Step 1：数据准备——让记忆库流动起来

**目标**：把 Anki 记忆库变成可被程序读取的素材库。

**做了什么**：
- 在无 GUI 的云端环境部署 Anki，打通与 AnkiWeb 的**双向增量同步**；
- 把 1848 张卡片按 8 个牌组导出为 Markdown 素材库（`anki_data/`）。

**踩坑**：
- Anki 同步偶发 `NetworkError`，不是逻辑错，重试即可；
- 无头环境需要 `QT_QPA_PLATFORM=offscreen`，否则启动即崩。

**技术沉淀**：数据准备层与内容生产层分离——**低频、重、一次性**的活（同步、导出）和**高频、轻、每天**的活（写作、发布）绝不混在一起。这样"每天跑"的任务不碰 Anki 原始数据。

---

# Step 2：隐私红线与素材打标

**目标**：素材库可以安全地公开写作，不泄露隐私。

**做了什么**：
- 三层隐私筛查：硬性个人标识 → 第一人称私人叙事 → 个人领域牌组；
- 隔离 11 条隐私卡片到 `_PRIVATE/`，与公开素材物理隔离；
- 对公开素材打标，建立兴趣画像（AI 与编程为核心，约占 52%）。

**踩坑**：隐私是**红线**，不是可选项。一旦泄露到公开仓库，几乎无法撤回。所以隔离目录要进 `.gitignore`，并设强制步骤——**隐私扫描失败即中止整条流水线**。

---

# Step 3：选题——去重与多样性

**目标**：每天从素材库选出值得写、且没写过的主题。

**做了什么**：
- 用 `state/used.md` 记录已用素材，实现**选题去重**；
- 按牌组**跨牌组均匀抽样**，保证选题多样性，而不是永远盯着同一个方向。

**技术沉淀**：状态落盘而非依赖记忆——`used.md`、`selected.json` 都在仓库里，任何 Agent 接手都能接着跑，**工作流无状态、可重跑、可移植**。

---

# Step 4：写作——Agent 协同与草稿闸门

**目标**：从素材到一篇可发布的博文。

**最初问题**：写作步骤（step05）一开始是**占位实现**——生成的标题和正文全是占位符，读不出真实内容，也接不上选题和素材。这等于"全自动链路在这里断掉了"。

**改造方案（Agent 协同写作）**：
- step04 选定主题后，step05 读取选定 + 对应素材，**装配出结构化底稿**（含真实素材要点摘录、章节骨架、写作指引），写入 `drafts/`；
- Agent 依据底稿撰写真实正文；
- 草稿闸门：草稿含占位符时 `live` 模式**不放行**，杜绝"占位博文污染正式博客"。

**踩坑（素材格式）**：Anki 卡片有**两种格式**——Quizify（`## Front/## Back`）和问答（`## 问题/## 答案/## 引用`）。解析时只认一种，就会把标题误提取成"问题"，还会导致文件名冲突、覆盖。必须两种都兼容。

**踩坑（frontmatter）**：新博文若没有标准 hexo frontmatter（`title/date/tags`），**Hexo 根本不渲染它**——线上就是 404。写作模板必须强制带 frontmatter。

---

# Step 5：构建与发布——从本地推到 CI

**目标**：把博文发布到 GitHub Pages，稳定、可复用。

**架构演进（最重要的一步）**：
- 一开始：本地 `hexo generate` + 推送几百个生成文件到 `gh-pages`；
- 后来：**只推源文件到 `main`**，由 GitHub Actions 在服务器端 `npm ci && hexo generate` 并自动部署。

这个迁移把"push 体积缩小了 10~20 倍"，构建也搬进了 GitHub 自己的网络——推送失败率大幅下降。

**这一路踩的坑最多**：

| 坑 | 根因 | 解法 |
|----|------|------|
| 自定义域名 404 | CNAME 被 `hexo clean` 删除 | 域名写进 `source/CNAME` + 发布校验 |
| 样式丢失 | `root` 路径硬编码为 `/blog/` | `root=/`、url 对齐 |
| 推送反复失败 | 国内访问 GitHub 443 不稳 | SSH over 443 + HTTPS 降级 + 指数退避 |
| 推 main 被拒 | main 含 workflow 需 `workflow` scope | 提供 workflow token；本地先 rebase 远程 |
| python 内调 bash 失败 | 沙箱限制 | 推送直接用 git 命令实现 |
| 本地远程 main 分叉 | 两边同时改 | 每次 push 前 fetch + rebase |

**技术沉淀（决策框架）**：出问题先**分层**——是传输层（网络/协议）还是架构层（部署模式本身）？别把重活放在弱链路上；把"防错的规则"写进 CI（如 CNAME 校验），而不是依赖人的记忆。

---

# 结语：把经验沉淀成秩序

回头看，这套工作流真正沉淀下来的不是某个工具，而是一套**方法论**：

1. **双层分离**：低频重活（数据准备）与高频轻活（内容生产）分层；
2. **状态落盘**：不依赖 Agent 记忆，无状态、可重跑、可移植；
3. **隐私红线**：隔离 + 强制步骤，宁可中止不可泄露；
4. **草稿闸门**：占位不放行，杜绝污染；
5. **配置外置**：路径、域名、凭据全部外置，换环境只改配置；
6. **根因分层**：先分传输层/架构层，再对症下药；
7. **CI 校验**：把防错规则写进流程，而非人的记忆。

这套系统从"能跑"到"好用"，靠的正是每一步的报错→反馈→修复。它现在可以被任意 Agent 接手，无人值守地完成"选材 → 写作 → 发布"。**构建工作流的过程，本身就是一次最好的工程实践。**
