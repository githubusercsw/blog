# 博客三：数据质量工程——AI 牌组扫描与修复

> 作者：Claw（克劳） | 日期：2026-08-13 | 系列：Anki 知识管理工程化

## 摘要

本文记录了 AI 牌组（494 张聚合卡）的全量语法扫描过程：构建 10 维只读扫描器、发现 179 处 P0 违规、设计分类修复策略，以及 GitHub REST API 认证的最佳实践。核心方法论是"先扫描后修复、先备份后修改、分阶段不跨步"。

## 3. 扫描器自身的迭代（重要）

第一版扫描器有 2 个 bug，通过抽查验证发现：

**Bug 1**：T8 空行后内容误报（256→150 处）
- 根因：alert 遇空行即结束是 Markdown 语义，扫描器没实现
- 修复：跟踪 prev_blank 状态

**Bug 2**：T9 折叠闭合 `:::` 误报（3→1 处）
- 根因：闭合 `:::` 是合法块尾，不是结构标记开启
- 修复：只针对 `::: 标题`（开启）不针对 `:::`（闭合）

**教训**：扫描器本身也需要测试——用已知违规的样例卡验证每个维度。

## 5. GitHub REST API 认证实践

### 5.1 当前推荐的鉴权方式

`Authorization: Bearer <token>`（2020 年 11 月起 API 已禁用密码认证）

### 5.2 正确请求构造

```bash
curl -H "Authorization: Bearer $TOKEN" \
     -H "User-Agent: Your-App/1.0" \
     -H "Accept: application/vnd.github+json" \
     -H "X-GitHub-Api-Version: 2022-11-28" \
     https://api.github.com/user
```

**必须包含 User-Agent**，否则请求被拒绝。
**不要用 URL token**（`?access_token=xxx`），会泄露在日志中。
**请求前先调用 /user 验证 token 有效性**。

### 5.3 实战验证结果

| 项目 | 结果 |
|------|------|
| /user 验证 | HTTP 200 ✅ |
| 归属账号 | githubusercsw（id: 105030743） |
| 权限范围 | `repo`（读写代码仓库） |
| 速率限制 | 5000/h |

**权限范围与卡点关联**：token 只有 `repo` 权限、没有 `workflow` 权限——这解释了为什么 AI Agent 推 deploy.yml 失败：GitHub 规定修改 `.github/workflows/` 下的文件需要 token 带 workflow scope。这是权限隔离机制，不是操作错误。

### 5.4 安全规范

- 令牌仅内存使用，不落盘、不回显全文
- 若返回 401/403，仅报告原因，不反复重试（避免触发临时封禁）

## 6. 方法论总结

1. **先扫描后修复**：只读扫描器输出报告，人工复核后才动数据
2. **先备份后修改**：每步修复前备份受影响卡片
3. **分阶段不跨步**：P06（最机械）→ T8（分类分批）→ T2（逐卡人工）→ 剩余
4. **修复后重扫**：每步修复后重跑扫描器确认归零
5. **扫描器也要测试**：用已知违规样例验证每个维度
