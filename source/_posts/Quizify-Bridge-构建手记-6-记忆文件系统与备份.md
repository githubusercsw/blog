# Quizify Bridge 构建手记（六）：把工程变成可恢复知识库

> 日期：2026-08-31

## 摘要

六篇手记的收尾，回到一个贯穿全程的元认知：**上下文是稀缺资源，输出要即时外部持久化**。本文讲我们如何用一套记忆文件系统 + 异地备份，让一个被打断很久的项目能冷启动恢复。

---

## 1. 为什么需要记忆文件系统

Agent 的上下文窗口有限，且会话会中断。如果不把中间结论落盘，下一次进来就是"失忆的重启"。我们搭了三层：

| 层 | 目录 | 作用 |
|----|------|------|
| 常驻 | `_memory/core/` | state/decisions/rules/map 四件套，恢复快照 |
| 按需 | `_memory/wiki/` | 验证体系、适配指南等，懒加载 |
| 溯源 | `_memory/raw/` | 仅追加归档，保留历史真相 |

**纪律**：core 常驻、wiki 按需、raw 溯源；状态推进仅过验证门后更新 `core/state.md`；日志只追加不修改。

## 2. 压缩边界锚定

长对话压缩时，在边界处写"锚点"摘要——保留关键信息锚点，丢弃流水细节。本系列博客本身也是一种锚点：把对话知识变成可回顾篇章。

## 3. 异地备份：Gitee 双仓

环境可能回收，本地工作会丢。我们推了两个仓库：

- `MasterAnki`：工程 + 记忆 FS + 验证蓝图（私有，防回收）。
- `blog`：本文所在的 Hexo 源文件仓库（自动构建发布）。

> 关键教训：token 这类密钥一旦进过日志就要轮转；备份用临时带 token 的 URL 推送，不写进 remote 配置。

## 4. 一图收尾

```
对话 → 即时持久化 → _memory/(core/wiki/raw)
     → 代码 + 测试 → /workspace/main/quizify-bridge
     → 异地备份 → Gitee(MasterAnki + blog)
```

把"易失的上下文"转成"持久的工程资产"，是这个项目最值钱的方法论。
